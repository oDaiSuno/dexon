# CI 与桌面发布

## 两条流程，各自负责什么

- `ci.yml`：每个 PR、`main` 更新和手动运行都执行完整门禁。保留 Linux x64、macOS arm64、macOS x64、Windows x64 单测，以及 Windows 原生助手、真实框架、桌面交互和四目标最终包验收。
- `release.yml`：只由版本标签或对版本标签的手动运行启动。再次调用同一套 CI，再构建最终发行文件；验收完成后只创建草稿，不自动公开。
- `CI required` 是配置到 GitHub 的唯一必需检查名称。它必须实际运行，而且所有必需任务都返回成功。失败、取消、跳过、缺失或无法解析的结果均不能放行。

工作流中的检查不能代替服务器设置。`main` 必须要求 PR、要求 `CI required`、要求分支保持最新，并禁止强推、删除和管理员绕过。个人项目不必为了合并自己的 PR 设置无法满足的他人审批数量。

静态检查只维护触发方式、权限、任务依赖、原生目标和固定版本等边界，不再用步骤名称、命令出现次数或旧安装包哈希的文字匹配冒充真实执行。

## 已消除的重复与保留的边界

Rust 安全工具在独立 Linux 任务中按固定版本安装并缓存，不再阻塞 Windows 单测的准备过程。缓存恢复后仍核对工具版本，漏洞和许可检查每次都执行。

CI 的质量任务使用 `verify --skip-unit-tests`，因为同一条必需流程已经在四个平台运行单测。直接运行 `npm run verify`、`npm run pack` 或 `npm run dist` 仍包含本地完整验证，不隐式跳过测试。

发布会重新运行 CI，再生成正式签名文件。这不是把之前的未签名包当成已验证的签名包；正式文件仍有独立的最终验收。暂不引入跨运行的结果复用服务。

## 最终文件验收

| 平台    | 实际验收入口                                                                                                    | 尚不能据此声称的能力                                               |
| ------- | --------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| macOS   | 解压最终 ZIP、只读挂载最终 DMG，在对应架构运行包内生产入口；正式发布额外检查签名、公证、开发者身份和 Gatekeeper | 不能代替每一种真实用户环境和应用内更新发现                         |
| Windows | 执行公开基准安装器、执行当前 NSIS 安装器、运行已安装程序、验证助手及其运行时文件锁、直接回退、正式卸载          | 不经过旧客户端发现和下载更新；未提供 Authenticode 身份             |
| Linux   | 从最终 AppImage 提取资源，配置并使用 SUID 沙箱启动；另以提取模式检查 AppImage 入口                              | 后一个入口检查关闭沙箱，不等于普通用户通过 FUSE 挂载启动的完整验收 |

验收前记录文件名、大小和 SHA-256；验收后再次核对，只有完全相同的文件才进入上传目录。更新元数据仍校验文件名、版本、大小、SHA-512 和 blockmap。

每个上传包包含 `*.manifest.json`，记录提交、运行编号、尝试编号、目标和签名状态。发布任务只下载明确指定的构建产物编号，再核对清单和全部文件。清单是对应关系，不是独立的安全背书；可信执行仍依赖受保护的源码、权限和成功任务。

同一次运行中重跑失败任务时，可以使用此前成功任务的同一候选；不能混入其他提交或其他运行的文件。尝试编号保留为记录，不机械要求全部任务的尝试编号相同。

## Windows 升级基准

唯一维护入口是 `.github/windows-upgrade-baseline.json`。其中记录公开版本、仓库、安装器名称、安装器 SHA-256，以及该版本助手的 SHA-256。

当前记录来自已公开的 `v0.1.0` 安装包及其 SBOM。它已经包含助手，因此回退必须恢复旧助手的准确内容，而不是要求助手目录消失。只有明确记录 `helperSha256: null` 的历史无助手版本才使用目录消失规则。

- PR 中若项目版本仍等于公开版本，显式进行同版本安装替换演练，报告为 `same-version-replacement`，不冒充跨版本升级。
- 正式发布必须使用更高版本，且基准必须对应最新公开稳定版本。
- 下载失败、哈希不符、记录缺失或版本不符都是失败，不会被解释成“首次发布”。
- 每次公开新版后，通过下一个受审查 PR 更新基准。哈希取自实际下载文件并与 GitHub 资产摘要核对；助手哈希还需与该版本包内清单及 SBOM 核对。

验收复用隔离的用户目录并要求每次启动生成新报告，但这不等于已经覆盖真实用户的所有设置、会话与数据迁移。发布前仍需用备份的典型用户数据进行人工演练。

## 首次使用正式 macOS 发布前

当前流程没有未签名降级路径。缺少签名或公证凭证时必须失败；PR 中的未签名 macOS 包只是开发验收产物，不能冒充正式可自动更新版本。

在 GitHub 的 `release` 环境中配置以下 secrets：

| 名称                          | 内容                                                                                 |
| ----------------------------- | ------------------------------------------------------------------------------------ |
| `MAC_CSC_LINK`                | 带密码的 Developer ID Application 签名证书，使用 electron-builder 支持的证书内容格式 |
| `MAC_CSC_KEY_PASSWORD`        | 证书密码                                                                             |
| `APPLE_ID`                    | 用于公证的 Apple 账号                                                                |
| `APPLE_APP_SPECIFIC_PASSWORD` | 对应的 App 专用密码                                                                  |

另在仓库 Actions variables 中配置公开的 `APPLE_TEAM_ID`。验收任务只读取这个身份编号，不接收签名私钥或公证密码。

将 `release` 环境限制为 `v*` 标签，并按实际维护人数设置人工批准。凭证只注入签名那一步；依赖安装、源码验证和独立包验收不接收这些凭证。

在仓库 Releases 设置中启用 **Immutable releases**。工作流会拒绝覆盖已公开版本，但仓库不可变设置才是阻止人工修改公开资产和标签的额外服务器保护。不要在流程上传过程中手动公开草稿。

Windows 目前明确是 **Unsigned Beta / Unknown Publisher**。正式的证书信任需要另行实现和验证，不能仅改名称消除这个限制。

## 发布下一个版本

仓库已经公开 `v0.1.0`，不能再次发布或覆盖这个版本。以下以 `0.1.1` 为例；若实际已有更新版本，应选择新的、更高的版本。

先合并 CI 修复 PR，然后为版本变更创建单独 PR：

```bash
nvm use
npm ci
git switch main
git pull --ff-only
git switch -c release/0.1.1
npm version 0.1.1 --no-git-tag-version
git add package.json package-lock.json
git commit -m "chore: 准备发布 0.1.1"
git push -u origin release/0.1.1
```

创建 PR，等待 `CI required` 真正成功，再按正常门禁合并。随后只给已合并的提交打标签：

```bash
git switch main
git pull --ff-only
git tag -a v0.1.1 -m "release: 发布 0.1.1"
git push origin v0.1.1
```

在 Actions 中查看 **Desktop release**。完成后检查草稿：

1. 所有必需任务成功，macOS 两个架构的最终验收都有结果。
2. 安装包、更新元数据、Windows SBOM、第三方声明和三份候选清单齐全。
3. 发布说明准确标注 Windows 未签名限制，不把安装器演练说成真实应用内更新成功。
4. 用下载到本地的最终文件做用户入口验收，并准备用户数据备份和恢复说明。
5. 确认不可变发布已启用，再手动公开草稿。

流程重跑只允许补充同一候选中尚未上传的文件。已有草稿中的同名文件若内容不同，流程会停止，不会自动覆盖或删除；应先人工审查这个草稿，再决定是否删除草稿并重新生成。已公开版本只能通过更高版本修复。

## 发布出问题时

- 尚未公开：保留失败日志和验收证据，修复后重新验证；不要手动替换某一个安装包或重签后沿用旧验收结论。
- 已经公开：不移动标签、不覆盖资产，发布更高版本的修复版。原客户端禁止自动降级，不要承诺自动回滚。
- 如需指导用户手动安装旧版，先备份数据并说明数据格式兼容边界。安装器能够回退，不代表新版数据一定能被旧程序读取。

暂不引入百分比分批发布、多渠道更新服务、全版本组合矩阵或独立指标平台。真实应用内预发布更新验收需要产品提供可控的候选更新源，不能单靠 CI 配置让旧客户端发现未公开的候选。
